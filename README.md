# CallbackApi

Go API for receiving callbacks from devices and systems, validating events, and making
them available for querying and management. The project also includes a React web
interface connected directly to the Go API.

## Intended outcome

The system should let a source send an event and receive confirmation that it was
accepted. The API validates the contract, records the current state in Redis, and places
the event in a Redis queue. A worker writes the snapshot to PostgreSQL.

The main screen in the React interface should show events in a table, with the newest
first according to the time the API received each event. Communication between the
browser and API is direct: HTTP to query and manage events, and Server-Sent Events (SSE)
to receive notifications about event creation, updates, and deletion.

> The React dashboard and event table are in the sibling `CallbackFrontEnd` project.
> Ordering by server receipt time remains future work in the API.

## Current status

- Go HTTP API with event contract validation.
- Redis for current state and stream-based queues.
- Worker that persists snapshots to PostgreSQL.
- Health/readiness, create, query, update, and delete routes for events.
- Account-authenticated Server-Sent Events (SSE) notifications for event creation, updates, and deletion.
- Email/password registration and sign-in with server-side sessions. Event routes
  require an authenticated session.
- Each event belongs to its creating account. Listing, retrieval, updates, and deletion
  are restricted to the authenticated owner.
- Duplicate protection on creation is scoped to the account and `source_id`.
- Versioned SQL migrations run with Tern. The initial migration is in
  [`migrations/001_initial_schema.sql`](migrations/001_initial_schema.sql); the hash
  column and its initial index are in
  [`migrations/002_event_deduplication.sql`](migrations/002_event_deduplication.sql),
  and the initial uniqueness per source is in
  [`migrations/003_unique_event_hash_per_source.sql`](migrations/003_unique_event_hash_per_source.sql).
- Authentication tables are created by
  [`migrations/004_authentication.sql`](migrations/004_authentication.sql). Registration
  is open; passwords are stored as Argon2id hashes, and sessions expire after seven
  days.
- Event ownership and per-account duplicate constraints are added by
  [`migrations/005_event_ownership.sql`](migrations/005_event_ownership.sql). Existing
  events are assigned automatically only when exactly one account exists; migration
  stops if ownership is ambiguous.
- Docker images and Kubernetes manifests for running the services.

Apply the authentication and event-ownership migrations before starting the updated API.
Use HTTPS in deployment; for local HTTP development, set `COOKIE_SECURE=false`.

Currently, the list route returns up to 100 active events from Redis and uses the
`created_at` value provided in the payload to sort them. To meet the intended outcome,
the API will need to record a server-generated receipt time and use it to sort the
table.

## Event contract

The create endpoint accepts `event_type`, `event_unique_hash`, and `payload`. The hash
is an opaque string generated by the sender. The payload must be a JSON object with
`source` (non-empty array), `source_id` (non-empty string), `data` (object),
`created_at` (RFC 3339 date and time), and `created_by` (non-empty string).

```json
{
  "event_type": "motion_detected",
  "event_unique_hash": "sender-generated-value-0001",
  "payload": {
    "source": ["camera-01"],
    "source_id": "front-door",
    "created_at": "2026-10-05T12:00:00Z",
    "created_by": "system-a",
    "data": {
      "message": "motion detected"
    }
  }
}
```

Before accessing PostgreSQL, the API checks Redis for hashes of the ten most recently
accepted events for the same account and `source_id`. A match returns `409 Conflict`.
If there is no match, PostgreSQL enforces permanent uniqueness for the (`user_id`,
`source_id`, `event_unique_hash`) tuple, covering hashes outside that window and
concurrent requests. After reserving the event in the database and enqueueing it in
Redis, the API updates the account-scoped list of recent hashes and responds with
`202 Accepted`. `created_at` continues to be used to sort events; it does not define
the deduplication window. The worker continues to process the event and operation
streams.

Before applying migration 003 to a database that already contains hashes, check for
duplicate pairs; creating the unique index fails while any remain:

```sql
SELECT source_id, event_unique_hash, count(*)
FROM events
WHERE source_id IS NOT NULL AND event_unique_hash IS NOT NULL
GROUP BY source_id, event_unique_hash
HAVING count(*) > 1;
```

## Architecture

```text
Source -- HTTP: callback --> Go API
                              ^   |
             HTTP: queries   |   | SSE: new events
                              |   v
                       React interface
                              |
                       main table

Go API --> Redis: state and queue --> Worker --> PostgreSQL
```

PostgreSQL stores persisted snapshots. Redis holds the state queried by the API and the
streams used by the worker. Tern applies the schema changes defined in versioned SQL
files.

## Available routes

| Method | Route | Description |
| --- | --- | --- |
| `GET` | `/v1/health` | Checks whether the API is responding. |
| `GET` | `/v1/health/ready` | Checks connections to PostgreSQL and Redis. |
| `POST` | `/v1/auth/register` | Creates an account and starts a session. |
| `POST` | `/v1/auth/login` | Signs in and starts a session. |
| `GET` | `/v1/auth/me` | Returns the current authenticated account. |
| `POST` | `/v1/auth/logout` | Ends the current session. |
| `DELETE` | `/v1/auth/account` | Deletes the authenticated account and its events after confirming the account email and password. |
| `GET` | `/swagger/` | Opens the interactive Swagger UI. |
| `GET` | `/openapi.yaml` | Returns the OpenAPI specification. |
| `POST` | `/v1/event/save` | Creates an event owned by the authenticated account. |
| `GET` | `/v1/events/stream` | Streams event creation, update, and deletion notifications for the account (SSE). |
| `GET` | `/v1/events/list` | Lists up to 100 active events owned by the account. |
| `GET` | `/v1/event/get/{id}` | Retrieves an event only if owned by the account. |
| `POST` | `/v1/event/update/{id}` | Updates an event only if owned by the account. |
| `PATCH` | `/v1/events/softdelete/{id}` | Soft-deletes an event only if owned by the account. |
| `DELETE` | `/v1/events/delete/{id}` | Permanently deletes an event only if owned by the account. |

## Integration tests

The API integration test uses Testify and exercises registration, API login,
session validation, event CRUD, and cross-account access restrictions. It requires
the API, PostgreSQL, and Redis to be running with the latest migrations applied.
The test creates and deletes two temporary accounts, so use a disposable test database.

```powershell
$env:CALLBACK_API_TEST_URL = "http://localhost:8080"
go test ./...
```

## Recommended next steps

- Record the server-side receipt time and sort by it, newest to oldest.
- Add password reset and email verification.

# CallbackApi


API em Go para receber callbacks de equipamentos e sistemas, validar eventos e
disponibilizá-los para consulta e gerenciamento. O projeto também prevê uma
interface web em React conectada diretamente à API Go.

## Resultado desejado

O sistema deverá permitir que uma origem envie um evento e receba a confirmação
de que ele foi aceito. A API valida o contrato, registra o estado atual no
Redis e coloca o evento em uma fila Redis. Um worker grava o snapshot no
PostgreSQL.

Na interface React, a tela principal deverá apresentar os eventos em uma
tabela, com os mais recentes primeiro segundo o horário em que a API recebeu
cada evento. A comunicação entre o navegador e a API será direta: HTTP para
consultar e gerenciar eventos e Server-Sent Events (SSE) para receber avisos de
criação, atualização e exclusão de eventos.

> O dashboard React e a tabela de eventos estão no projeto irmão
> `CallbackFrontEnd`. A ordenação pelo horário de recebimento gerado no servidor ainda é um trabalho futuro na API.

## Estado atual

- API HTTP em Go com validação do contrato de eventos.
- Redis para estado atual e filas em streams.
- Worker que persiste snapshots no PostgreSQL.
- Rotas de health/readiness, criação, consulta, atualização e exclusão de
  eventos.
- Notificações Server-Sent Events (SSE) autenticadas para criação, atualização e exclusão de eventos.
- Cadastro e login com email e senha, usando sessões gerenciadas pela API. As
  rotas de eventos exigem uma sessão autenticada.
- Cada evento pertence à conta que o criou. Listagem, consulta, atualização e exclusão
  são restritas ao proprietário autenticado.
- A proteção contra duplicidade é restrita à conta e ao `source_id`.
- Migrations SQL versionadas executadas com Tern. A migration inicial está em
  [`migrations/001_initial_schema.sql`](migrations/001_initial_schema.sql); a
  coluna de hash e seu índice inicial estão em
  [`migrations/002_event_deduplication.sql`](migrations/002_event_deduplication.sql),
  e a unicidade inicial por emissor está em
[`migrations/003_unique_event_hash_per_source.sql`](migrations/003_unique_event_hash_per_source.sql).
- As tabelas de autenticação são criadas por
  [`migrations/004_authentication.sql`](migrations/004_authentication.sql). O
  cadastro é aberto; as senhas são armazenadas como hashes Argon2id e as sessões
  expiram após sete dias.
- O vínculo dos eventos com seus proprietários e a unicidade por conta são adicionados
  por [`migrations/005_event_ownership.sql`](migrations/005_event_ownership.sql).
  Eventos existentes são atribuídos automaticamente somente quando há exatamente uma
  conta; a migration para se o proprietário não puder ser determinado.
- Imagens e manifests Docker/Kubernetes para executar os serviços.

As migrations de autenticação e de propriedade dos eventos precisam ser aplicadas
antes de iniciar a API atualizada. Use HTTPS em produção; para desenvolvimento local
com HTTP, defina `COOKIE_SECURE=false`.

Atualmente, a rota de listagem retorna até 100 eventos ativos do Redis e usa o
`created_at` informado no payload para ordená-los. Para atender ao resultado
desejado, a API precisará registrar um horário de recebimento gerado no servidor
e usá-lo na ordenação da tabela.

## Contrato do evento

O endpoint de criação recebe `event_type`, `event_unique_hash` e `payload`. O hash
é uma string opaca gerada pelo emissor. O payload deve ser um objeto JSON com
`source` (array não vazio), `source_id` (string não vazia),
`data` (objeto), `created_at` (data e hora RFC 3339) e `created_by` (string não
vazia).

```json
{
  "event_type": "motion_detected",
  "event_unique_hash": "sender-generated-value-0001",
  "payload": {
    "source": ["camera-01"],
    "source_id": "front-door",
    "created_at": "2026-10-05T12:00:00Z",
    "created_by": "system-a",
    "data": {
      "message": "motion detected"
    }
  }
}
```

Antes de acessar PostgreSQL, a API consulta no Redis os hashes dos dez eventos
mais recentemente aceitos para a mesma conta e `source_id`. Uma correspondência
retorna `409 Conflict`. Se não houver correspondência, PostgreSQL impõe unicidade
permanente à tupla (`user_id`, `source_id`, `event_unique_hash`), cobrindo hashes
fora dessa janela e requisições concorrentes. Depois de reservar o evento no banco e
enfileirá-lo no Redis, a API atualiza a lista de hashes recentes da conta e responde
`202 Accepted`. O `created_at` continua sendo usado para ordenar os eventos; ele
não define a janela de deduplicação. O worker continua processando os streams de
eventos e operações.

Antes de aplicar a migration 003 em um banco que já recebeu hashes, confira se
há pares duplicados; a criação do índice único falha enquanto eles existirem:

```sql
SELECT source_id, event_unique_hash, count(*)
FROM events
WHERE source_id IS NOT NULL AND event_unique_hash IS NOT NULL
GROUP BY source_id, event_unique_hash
HAVING count(*) > 1;
```

## Arquitetura

```text
Origem -- HTTP: callback --> API Go
                              ^   |
             HTTP: consultas |   | SSE: novos eventos
                              |   v
                       Interface React
                              |
                       tabela principal

API Go --> Redis: estado e fila --> Worker --> PostgreSQL
```

O PostgreSQL guarda os snapshots persistidos. Redis mantém o estado consultado
pela API e os streams usados pelo worker. O Tern aplica as alterações de schema
definidas em arquivos SQL versionados.
